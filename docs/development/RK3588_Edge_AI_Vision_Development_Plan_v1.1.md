# 基于 RK3588 的边缘 AI 视觉与本地大模型分析终端

**正式开发步骤与验收计划**  
文档版本：v1.1  
状态：开发基线草案  
项目范围文件：docs/project/RK3588_Edge_AI_Vision_Project_Scope_v1.1.md

## 1. 开发原则

1. 每个阶段先明确输入、产物和验收条件，验收通过后再进入下一阶段。
2. 先使用板卡厂商提供的稳定镜像和参考程序确认硬件，再写项目自己的程序。
3. 每次只引入一个新层次：先采集，再建立视觉基线，分别验证 RKNN 与 RKLLM，再做并发集成、编码联网和 UI。
4. 任何性能数字都同时记录环境、输入、版本、测试时长和测量方法。
5. 不复制整套厂商 SDK 到仓库；记录依赖清单、版本、来源和许可，项目补丁单独管理。
6. 先保证可恢复的稳定基线，再进行内核、设备树和驱动实验。
7. 第一版仅实现 RK3588 单板链路；其他 MCU 和 i.MX6ULL 暂不纳入验收范围。
8. RKNN 视觉模型与 RKLLM 语言模型使用不同工具链；DeepSeek 只做异步事件分析和问答，不放入逐帧视觉处理闭环。

## 2. 仓库目录准备

在现有仓库中沿用已有的 RK3588 目录，按阶段补充以下位置，不必一次创建所有空目录：

```text
docs/
├── architecture/decisions/
├── boards/rk3588/
├── development/
└── project/

software/linux/rk3588/
├── apps/
│   ├── camera/
│   ├── diagnostics/
│   ├── streaming/
│   ├── ui/
│   ├── vision/
│   └── llm/
├── device-tree/overlays/
├── drivers/media/i2c/imx415/
├── kernel/{config-fragments,patches}/
└── tests/

software/host/{app,tests,tools}/
common/protocol/{examples,spec}/
tests/{acceptance,integration}/
tools/{capture,deploy,scripts}/
```

目录规则：

- 文档放 docs，板卡实测资料放 docs/boards/rk3588。
- 项目自有源码只放 software、common、tools 和 tests。
- 不把下载下来的完整 Linux SDK、厂商内核、模型训练数据或编译产物放入仓库。
- 每个阶段只创建当期需要的目录，并用 README 或 .gitkeep 保留确有用途的空目录。
- 原有多板空目录先保留，避免在没有盘点前删除；新主线的提交只修改本阶段相关文件。

## 3. 阶段 0：确定新项目基线和仓库边界

### 要做什么

- 将项目主线确定为“基于 RK3588 的边缘 AI 视觉分析终端”。
- 将项目范围文件、开发步骤文件和板卡基线模板放到上表位置。
- 更新根 README：说明当前第一版只支持 RK3588，并链接到总体范围和开发步骤。
- 对旧的多板方案文档标记状态：历史方案或待整理，不要让旧计划与新计划同时被误认为当前执行路线。
- 记录仓库当前分支、远端、最近提交和工作区状态，先建立一个干净提交点。

### 产物

- 项目范围文件和正式开发步骤文件。
- README 中的项目定位和文档入口。
- 已经确认的需求与待确认事项清单。

### 验收

- 新旧项目目标不会在 README 和开发计划中互相矛盾。
- 文档能明确说明不使用哪些开发板、当前不做哪些功能。
- 新提交只包含文档和目录框架，不混入 SDK、固件镜像或二进制依赖。

## 4. 阶段 1：盘点硬件和软件环境

### 要做什么

- 填写 docs/boards/rk3588/RK3588_Board_Baseline_Template_v1.1.md。
- 拍照记录核心板、底板、IMX415 模块、排线、屏幕和电源的型号与连接方式。
- 记录系统镜像、内核、设备树、厂商 SDK、编译器、RKNPU 驱动、RKNN Runtime、RKLLM Runtime/Toolkit、MPP、RGA、显示栈版本。
- 检查启动日志、相机和显示相关设备节点、V4L2/Media Controller 拓扑、网络接口和可用存储。
- 确认风扇或散热器、电源规格和板卡温度读取方式。
- 备份当前可启动镜像或记录可靠恢复流程。

### 产物

- 完整的板卡基线表。
- SDK 和系统镜像的来源、许可、版本和校验值记录。
- 已知问题清单和恢复步骤。

### 验收

- 硬件型号和软件版本可由另一台电脑上的开发者重复确认。
- 具备从误配置中恢复到可启动系统的办法。
- 明确相机接口和屏幕接口，而不是只知道 SoC 型号。

## 5. 阶段 2：确认厂商参考功能和构建部署流程

### 要做什么

- 使用当前镜像自带或配套的摄像头、显示、RGA、NPU 和编码测试程序。
- 逐项确认哪些模块在当前镜像确实可用，哪些仅在资料或芯片规格中存在。
- 在 Ubuntu 开发机上建立与板端 ABI 匹配的交叉编译环境，先编译一个最小用户态程序并部署运行。
- 记录编译、传输、启动、日志收集和回退方式。
- 保存依赖清单，不将厂商 SDK 整包提交到 Git。

### 产物

- 编译和部署说明。
- 可重复运行的最小程序。
- 当前镜像已验证的硬件能力矩阵。

### 验收

- 开发机能编译出板端可运行程序。
- 程序可部署、启动、输出日志并正常退出。
- 通过实测区分“硬件具备”“驱动启用”“当前程序可调用”三个状态。

## 6. 阶段 3：打通本地显示和网络基础

### 要做什么

- 先确认板端屏幕或 HDMI 显示独立可用，记录接口、分辨率和刷新率。
- 确认板端有线网络和电脑之间可稳定通信。
- 建立项目自己的状态页或简单显示程序，展示板卡版本、网络状态和运行时间。
- 确认电脑端可连接板端并保存测试日志。

### 产物

- 板端显示检查记录。
- 电脑到板端的网络连通记录。
- 本地运行状态界面初版。

### 验收

- 重启后显示功能可以重复启动。
- 电脑可持续连接板端并接收状态信息。
- 显示或联网问题可与摄像头、AI 模型问题分开定位。

## 7. 阶段 4：完成摄像头采集和 V4L2 诊断

### 要做什么

- 使用板卡当前可用驱动和设备树启动 IMX415。
- 记录 Media Controller 拓扑、传感器模式、CSI/ISP 节点和 /dev/video 节点对应关系。
- 编写项目自己的采集诊断程序：枚举能力和格式、启动/停止采集、记录帧序号、时间戳、帧间隔、错误和丢帧。
- 用至少两种运行时长检查稳定性，并记录相机模式和曝光设置。
- 如果现成驱动不可用，再另立任务研究 IMX415 传感器子设备驱动和设备树；不直接改写 ISP 或 CSI 主控驱动。

### 产物

- 摄像头连接图和节点说明。
- 采集诊断工具。
- 不同相机模式的稳定性记录。

### 验收

- 可按记录的步骤启动采集并获得正确图像。
- 采集帧计数、时间戳和丢帧统计可信。
- 长时间运行无持续增长的错误、资源泄漏或无法恢复的卡死。
- 任何设备树或驱动改动都能追溯到具体版本并可回退。

## 8. 阶段 5：建立 CPU 软件基线

### 要做什么

- 将采集图像送入简单的 CPU 图像处理和本地显示流程。
- 选择固定的相机模式和输入场景，建立处理时间、帧率、CPU 占用、内存占用和温度基线。
- 如果开始视频流传输，先使用最简单可验证的编码路径，并记录编码和网络延迟。
- 用统一时间戳测量采集到显示、采集到编码的端到端延迟。

### 产物

- 可重复的 CPU 基线程序和测量记录。
- 输入样本、测试条件和测量方法。

### 验收

- 同一设置重复测试结果处于可解释的波动范围内。
- 每个统计值都能说明输入、配置、时长和软件版本。
- 发现瓶颈前不提前宣称零拷贝或硬件加速收益。

## 9. 阶段 6：引入 RGA 和 DMA-BUF 缓冲区

### 要做什么

- 先使用 RGA 完成单一明确操作，例如缩放或色彩格式转换。
- 将 RGA 结果与 CPU 路径做图像正确性和耗时对比。
- 然后检查 V4L2、RGA、NPU、MPP 和显示之间能否使用兼容的 DMA-BUF 缓冲区。
- 逐段验证格式、步幅、对齐、生命周期和同步；任何不兼容处先使用显式复制的稳定路径。
- 对共享缓冲路径做压力测试，检查花屏、撕裂、缓存一致性和文件描述符泄漏。

### 产物

- RGA 处理模块。
- 不同路径的对照测量表。
- DMA-BUF 能否共享的实测结论和限制。

### 验收

- 图像正确性经过固定样本对比。
- RGA 路径确实由硬件库和驱动完成，而不是仅凭 API 名称推断。
- 若称为零拷贝，必须提供缓冲区流转和测量证据；否则如实写成共享缓冲或减少一次复制。

## 10. 阶段 7：接入 RKNN NPU 模型

### 要做什么

- 先使用 RKNN 官方示例模型验证 Runtime 和 NPU 驱动版本匹配。
- 选择第一版轻量模型，在开发机上完成转换和精度检查，模型文件版本和许可一并记录。
- 先用固定图片验证板端推理，再接入实时摄像头。
- 记录预处理、NPU 推理、后处理和端到端时间，比较输入尺寸、精度和吞吐的折衷。
- 先采用稳定的单模型配置，确认负载和散热后再测试 NPU 多核或多任务。

### 产物

- 模型转换和部署说明。
- 推理模块及输入输出定义。
- PC 原模型与板端 RKNN 结果对照记录。

### 验收

- 模型在目标镜像和 Runtime 上可重复加载、推理和释放。
- 结果正确性有验证样本和对照记录。
- 有 NPU 时间、端到端时间、内存使用和温度记录。
- 模型文件来源、许可证、版本和校验值明确。

## 11. 阶段 8：部署 DeepSeek-R1-Distill 本地模型

### 要做什么

- 确认当前板卡镜像、RKNPU 驱动和 RKLLM Runtime 版本相互匹配，先运行配套示例。
- 在开发机上按 Rockchip RKLLM Toolkit 流程准备模型；板端使用 RKLLM Runtime 推理，不把 LLM 模型当作 RKNN 视觉模型转换。
- 对 4GB 内存版本，第一候选为 DeepSeek-R1-Distill-Qwen-1.5B 的量化版本；正点原子教程对其 4GB 配置给出的范围为 1.5B，7B 不作为本板基线目标。
- 先单独启动 LLM，记录模型加载时间、首 token 延迟、生成速度、内存峰值和温度。
- 再将视觉检测结果保存为带时间戳的结构化事件，让 LLM 按用户提问总结事件或解释设备状态。
- LLM 采用异步任务；不要求每一帧都传入大模型，也不允许它阻塞采集、实时检测或编码。
- 分别测试 LLM 单独运行、与摄像头/视觉模型并发运行、按需启动三种模式。若并发导致内存或性能不稳定，保留按需/分时策略。

### 产物

- RKLLM 运行环境和模型版本记录。
- 板端本地问答/事件总结最小程序。
- LLM 单独及并发负载对比表。
- 模型许可证、来源、量化配置和文件哈希记录。

### 验收

- 在不依赖云端的情况下完成至少一轮本地问答。
- 能确认运行的是 RKLLM Runtime 和目标 RKLLM 模型，而不是 CPU 上的占位推理或云端 API。
- 记录首 token 延迟、生成 token/s、内存峰值、温度和模型配置。
- 与视觉链路并发时记录丢帧、延迟、内存和温度；若不能稳定并发，项目通过按需或分时策略验收，并在操作说明中说明限制。
- 电脑端可以通过板端服务发送查询并接收模型回答；断网时板端本地问答仍可工作。
## 12. 阶段 9：使用 MPP 编码并建立电脑端视频预览

### 要做什么

- 先用 MPP 官方测试程序确认编码器、格式、分辨率和帧率组合。
- 将实时采集帧接入硬件编码路径，记录输入和输出时间戳、码率、编码延迟和错误。
- 选择一种协议实现第一版传输，例如 RTSP；另用轻量控制/状态通道传输配置和指标。
- 电脑端先验证视频连续播放，再集成项目自己的预览和状态界面。
- 处理网络断开、客户端退出和板端服务重启等恢复场景。

### 产物

- 板端编码和流服务。
- 电脑端实时预览。
- 网络断连和恢复记录。

### 验收

- 电脑端可以连续观看目标摄像头画面。
- 录像或抓帧可确认没有持续增长的编码错误。
- 码率、分辨率、帧率、网络占用和延迟均有记录。
- 客户端断开后重新连接无需重启整块板卡。

## 13. 阶段 10：完成板端 UI、电脑端监控和项目协议

### 要做什么

- 板端显示实时画面、检测结果、FPS、运行时间、温度和设备状态。
- 电脑端展示视频、推理结果、系统指标和日志，并提供必要的运行配置项。
- 将板端与电脑端消息定义写入 common/protocol/spec，消息包含版本、类型、时间戳、字段范围和错误响应。
- 对远程配置做参数边界校验；远程端不能绕过板端安全检查直接改设备底层状态。
- 配置、状态和日志通道与视频流分开，避免大视频数据阻塞控制消息。

### 产物

- 板端 UI 和电脑端监控程序。
- 协议规范及最小示例。
- 日志导出和参数配置说明。

### 验收

- UI 不阻塞采集、推理和编码主流程。
- 网络异常后状态能显示为离线或过期，而不是伪装为实时数据。
- 不支持或非法参数会被拒绝并返回可理解的错误。
- PC 重连后可以恢复预览和状态读取。

## 14. 阶段 11：系统集成和性能优化

### 要做什么

- 固定相机模式、模型、视频编码参数和测试场景。
- 对照 CPU 基线，逐项比较 RGA、NPU、MPP、DMA-BUF 和线程调度优化的实际收益。
- 使用系统可用的性能分析工具观察 CPU、内存、频率、温度、线程等待和丢帧。
- 分析瓶颈属于传感器、ISP、缓冲复制、预处理、NPU、编码、显示还是网络。
- 优先优化影响最大且可复现的瓶颈；每次修改后重跑相同基准。
- 确定默认运行参数和 4GB 内存下的缓冲区数量上限。

### 产物

- 优化前后结果表。
- 性能瓶颈分析和决策记录。
- 默认配置及已知性能限制。

### 验收

- 每项优化都有同环境对照数据，且能解释收益或回退原因。
- 不以短暂峰值替代稳定运行结果。
- 长时间运行时温度、内存和帧率变化有记录。
- 目标指标在本阶段根据真实基线确认并写入最终验收表。

## 15. 阶段 12：稳定性、部署和最终验收

### 要做什么

- 制作可重复安装和启动的部署包或部署脚本。
- 添加服务自动启动、日志轮转、配置校验和异常退出后的恢复机制。
- 按实际冻结的目标参数进行至少一次长时间连续运行；建议覆盖冷启动、网络断开、客户端重连、摄像头重新启动和服务重启。
- 记录所有问题、复现步骤和修复提交。
- 编写用户操作说明、开发环境复建说明、升级与回退说明。
- 生成最终性能报告，所有数字标注实测条件。

### 最终验收清单

- 从干净工作区按文档能够构建和部署。
- 一路摄像头采集、RKNN 视觉推理、MPP 编码、板端显示和电脑端视频预览可同时运行。
- 连续运行时无不可恢复崩溃、明显资源泄漏或未解释的持续丢帧。
- 摄像头、RKNN 视觉模型、RKLLM DeepSeek 模型、编码和协议配置有版本记录。
- 主要延迟、帧率、丢帧、CPU/内存、温度、网络码率，以及 LLM 首 token 延迟和 token/s 都有实测报告。
- 有日志、问题排查、重启和回退说明。
- README、项目范围、开发计划、板卡基线和测试记录之间相互一致。
